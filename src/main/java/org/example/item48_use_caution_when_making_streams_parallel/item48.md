# آیتم ۴۸: هنگام موازی‌سازی Streamها با احتیاط عمل کنید

## (Use caution when making streams parallel)

> **پیام اصلی:** موازی‌سازی یک ابزار بهینه‌سازی است، نه یک بهینه‌سازی تضمین‌شده. باید هم صحت برنامه و هم عملکرد واقعی آن را بررسی کنیم.

از Java 8 به بعد، موازی‌سازی یک Stream بسیار ساده شده است؛ اغلب فقط کافی است `.parallel()` را به pipeline اضافه کنیم:

<div dir="ltr">

```java
numbers.parallelStream()
    .filter(this::isValid)
    .map(this::process)
    .toList();
```
</div>

اما آیا نسخه‌ی موازی حتماً سریع‌تر است؟ آیا نتیجه‌ی آن همیشه یکسان خواهد بود؟ آیا ممکن است برنامه بسیار کند شود؟ **پاسخ هر سه سؤال به شرایط بستگی دارد.**

<a id="why-not-always"></a>
## ۱. چرا موازی‌سازی Stream همیشه مفید نیست؟

| مفهوم | توضیح |
|-------|-------|
| **Concurrency (هم‌روندی)** | چند کار در بازه‌های زمانی هم‌پوشان پیش می‌روند |
| **Parallelism (موازی‌سازی)** | چند کار واقعاً هم‌زمان روی چند هسته‌ی پردازنده اجرا می‌شوند |

**هزینه‌های اجرای موازی:**

- تقسیم داده‌ها به بخش‌های کوچک‌تر
- زمان‌بندی و مدیریت کارها
- هماهنگی بین Threadها
- ترکیب نتایج بخش‌های مختلف
- احتمال رقابت بر سر منابع مشترک
- هزینه‌ی انتقال داده بین حافظه و Cache پردازنده

> **اگر کار هر عنصر سبک باشد، ممکن است این هزینه‌ها از سود اجرای موازی بیشتر شوند.**

<a id="mersenne-example"></a>
## ۲. مثال اول کتاب: تولید اعداد اول مرسن

$$ M_p = 2^p - 1 $$

که در آن $p$ یک عدد اول است و خود $M_p$ نیز باید اول باشد:

$$ 2^2 - 1 = 3 \quad , \quad 2^3 - 1 = 7 $$

<a id="sequential"></a>
### نسخه‌ی ترتیبی

<div dir="ltr">

```java
public static void main(String[] args) {
    primes()
        .map(p -> TWO.pow(p.intValueExact()).subtract(ONE))
        .filter(mersenne -> mersenne.isProbablePrime(50))
        .limit(20)
        .forEach(System.out::println);
}

static Stream<BigInteger> primes() {
    return Stream.iterate(TWO, BigInteger::nextProbablePrime);
}
```
</div>

| مرحله | عملیات |
|--------|--------|
| ۱ | تولید Stream از اعداد اول با `Stream.iterate` |
| ۲ | تبدیل هر $p$ به $2^p - 1$ |
| ۳ | بررسی اول‌بودن با `isProbablePrime(50)` |
| ۴ | توقف پس از یافتن ۲۰ عدد مناسب |
| ۵ | چاپ نتایج |

> **طبق اندازه‌گیری نویسنده روی سیستم خودش:** اجرای این برنامه حدود **۱۲٫۵ ثانیه** طول کشیده است.

**افزودن `.parallel()`:**

<div dir="ltr">

```java
primes()
    .parallel()
    .map(p -> TWO.pow(p.intValueExact()).subtract(ONE))
    .filter(mersenne -> mersenne.isProbablePrime(50))
    .limit(20)
    .forEach(System.out::println);
```
</div>

> **نتیجه:** برنامه چیزی چاپ نمی‌کرد، استفاده از CPU به حدود ۹۰ درصد می‌رسید و این وضعیت ادامه پیدا می‌کرد. نویسنده پس از نیم ساعت برنامه را متوقف کرد.

> **این رفتار نمونه‌ای از Liveness Failure است:** برنامه از نظر اجرای دستورها فعال است، اما در عمل پیشرفت مفیدی ندارد (این لزوماً Deadlock نیست).

<a id="why-fails"></a>
## ۳. چرا این pipeline در حالت موازی شکست می‌خورد؟

<a id="iterate"></a>
### عامل اول: `Stream.iterate`

<div dir="ltr">

```java
Stream.iterate(TWO, BigInteger::nextProbablePrime)
```
</div>

هر عنصر بر اساس عنصر قبلی محاسبه می‌شود. برای به‌دست‌آوردن عدد اول بعدی، باید از عدد قبلی شروع کنیم.

```
آرایه (قابل تقسیم):               Stream.iterate (وابسته):
[0, 1, 2, 3, 4, 5, 6, 7]         x₀ → x₁ → x₂ → x₃ → x₄ → ...
       │
   تقسیم داده
    /       \
[0,1,2,3]  [4,5,6,7]              ❌ تقسیم دشوار است
```

<a id="limit"></a>
### عامل دوم: عملیات `limit`

<div dir="ltr">

```java
.limit(20)
```
</div>

| حالت | رفتار |
|------|--------|
| **ترتیبی** | برنامه به‌ترتیب عناصر را تولید می‌کند و پس از یافتن ۲۰ عدد متوقف می‌شود |
| **موازی** | چند Thread ممکن است بخش‌های مختلف را پردازش کنند و عناصر بیشتری پردازش شوند |

**مشکل اصلی:** هزینه‌ی محاسبه‌ی اعداد اول مرسن با بزرگ‌ترشدن توان‌ها به‌شدت افزایش پیدا می‌کند. یافتن یک نتیجه‌ی اضافه ممکن است بسیار گران تمام شود — حتی با هزینه‌ی محاسبه‌ی تمام نتایج قبلی قابل‌مقایسه باشد.

> **هشدار:** اگر pipeline شامل `Stream.iterate` یا عملیات کوتاه‌کننده‌ای مانند `limit` باشد، باید پیش از موازی‌سازی، عملکرد و رفتار آن را با دقت بررسی کنیم.

<a id="good-sources"></a>
## ۴. چه منابعی برای موازی‌سازی مناسب‌ترند؟

| منبع داده | مناسب برای موازی‌سازی |
|-----------|---------------------|
| `ArrayList` | ✅ |
| `HashMap` | ✅ |
| `HashSet` | ✅ |
| `ConcurrentHashMap` | ✅ |
| آرایه‌ها | ✅ |
| محدوده‌های `IntStream` و `LongStream` | ✅ |
| `Stream.iterate` | ⚠️ |
| `LinkedList` | ❌ |
| `Stream.of(...)` با منبع نامشخص | ⚠️ |

<a id="splittability"></a>
### الف) تقسیم‌پذیری مناسب

این ساختارها امکان تقسیم داده‌ها به بخش‌های کوچک‌تر را به‌صورت نسبتاً دقیق و کم‌هزینه فراهم می‌کنند:

```
آرایه ۱ میلیون عنصری:
[────بخش ۱────][────بخش ۲────][────بخش ۳────][────بخش ۴────]
    Thread 1      Thread 2      Thread 3      Thread 4
```

<a id="locality"></a>
### ب) Locality of Reference

| ساختار | Localities |
|--------|-----------|
| آرایه‌های primitive | ✅ بسیار خوب — مقادیر متوالی در حافظه |
| ساختارهایی با ارجاع به اشیای دیگر | ⚠️ پراکنده — افزایش Cache Miss |

> **نتیجه:** برای موازی‌سازی، فقط تعداد عناصر مهم نیست؛ نحوه‌ی تقسیم داده و الگوی دسترسی به حافظه نیز اهمیت زیادی دارد.

<a id="spliterator"></a>
## ۵. نقش `Spliterator` در موازی‌سازی

Stream برای تقسیم منبع داده از `Spliterator` استفاده می‌کند.

```
Spliterator
    │
    ├── trySplit() → بخشی از عناصر را جدا می‌کند
    │
    └── برای Threadهای مختلف قابل واگذاری است
```

> **نکته:** اگر خودمان `Stream`، `Iterable` یا `Collection` سفارشی پیاده‌سازی کنیم و بخواهیم اجرای موازی خوبی داشته باشیم، ممکن است لازم باشد `spliterator()` را به‌شکل مناسبی بازنویسی کنیم و عملکرد آن را در شرایط واقعی بسنجیم.

> **ساخت یک `Spliterator` باکیفیت کار ساده‌ای نیست.**

<a id="terminal-importance"></a>
## ۶. نوع عملیات پایانی هم اهمیت دارد

<a id="reduction"></a>
### عملیات کاهش (Reduction)

<div dir="ltr">

```java
long total = numbers.parallelStream()
    .mapToLong(Integer::longValue)
    .sum();

Optional<Integer> max = numbers.parallelStream()
    .max(Integer::compareTo);
```
</div>

```
مجموع کل
    │
    ├── بخش ۱ → مجموع جزئی A
    ├── بخش ۲ → مجموع جزئی B
    └── بخش ۳ → مجموع جزئی C
             │
             ▼
      ترکیب نتایج جزئی
```

| عملیات | مناسب برای موازی‌سازی |
|--------|---------------------|
| `sum`، `count` | ✅ |
| `min`، `max` | ✅ |
| `anyMatch`، `allMatch`، `noneMatch` | ✅ (با شرایط) |
| `collect` (بسته به Collector) | ⚠️ |

<a id="collect-cost"></a>
### چرا بعضی عملیات `collect` ممکن است پرهزینه باشند؟

<div dir="ltr">

```java
List<String> result = words.parallelStream()
    .filter(word -> word.length() > 5)
    .collect(Collectors.toList());
```
</div>

> **در اجرای موازی:** چند Thread ممکن است ساختارهای میانی جداگانه‌ای بسازند و سپس نتایج آن‌ها با هم ترکیب شوند. این ترکیب می‌تواند هزینه داشته باشد.

> **نکته مهم:** نباید نتیجه گرفت که `collect` ذاتاً برای موازی‌سازی نامناسب است. بعضی Collectorها می‌توانند به‌خوبی به‌صورت موازی کار کنند.

<a id="safety-failure"></a>
## ۷. خطر دوم: موازی‌سازی ممکن است نتیجه‌ی نادرست تولید کند

<a id="shared-state"></a>
### مثال: تغییر وضعیت مشترک در `forEach`

<div dir="ltr">

```java
// ❌ ناایمن در حالت موازی
List<Integer> result = new ArrayList<>();

numbers.parallelStream()
    .forEach(result::add);
```
</div>

`ArrayList` برای دسترسی هم‌زمان طراحی نشده است. ممکن است بعضی عناصر از دست بروند.

**راه طبیعی:**

<div dir="ltr">

```java
// ✅
List<Integer> result = numbers.parallelStream()
    .collect(Collectors.toList());
```
</div>

> **ارتباط با Item 46:** استفاده از توابع بدون عوارض جانبی و اجتناب از تغییر وضعیت مشترک، طراحی Stream را قابل‌اعتمادتر می‌کند.

<a id="reduction-conditions"></a>
### شرط‌های مهم توابع در عملیات کاهش

| شرط | توضیح |
|------|-------|
| **Associative** | گروه‌بندی عملیات نباید نتیجه را تغییر دهد: $(a+b)+c = a+(b+c)$ |
| **Stateless** | نتیجه نباید به وضعیت قابل‌تغییر وابسته باشد |
| **Non-interfering** | تابع نباید منبع داده‌ی Stream را در حین پردازش تغییر دهد |

> **نکته درباره‌ی اعداد اعشاری:** در محاسبات ممیز شناور، به دلیل گردکردن اعداد، تغییر ترتیب عملیات می‌تواند اختلاف‌های عددی کوچکی ایجاد کند.

<a id="foreach-vs-ordered"></a>
## ۸. تفاوت `forEach` و `forEachOrdered`

<div dir="ltr">

```java
// ترتیب تضمین‌شده نیست
.forEach(System.out::println);

// ترتیب حفظ می‌شود
.forEachOrdered(System.out::println);
```
</div>

| عملیات | تضمین ترتیب |
|--------|-------------|
| `forEach` | ❌ ترتیب مواجهه را تضمین نمی‌کند |
| `forEachOrdered` | ✅ ترتیب مواجهه را حفظ می‌کند |

> **نکته:** حفظ ترتیب می‌تواند بخشی از مزایای اجرای موازی را کاهش دهد. همچنین `forEachOrdered` مشکل اصلی مثال اعداد اول مرسن را برطرف نمی‌کند.

<a id="when-worth"></a>
## ۹. چه زمانی موازی‌سازی واقعاً ارزش دارد؟

> **تخمین تقریبی کتاب:** حاصل‌ضرب تعداد عناصر Stream در تعداد خطوط کدی که برای پردازش هر عنصر اجرا می‌شود، دست‌کم در حدود **۱۰۰٬۰۰۰** باشد.

> **این یک قانون قطعی یا معیار استاندارد امروزی نیست؛ فقط یک راهنمای سرانگشتی است.**

**برای تصمیم‌گیری واقعی باید بررسی کنیم:**

| عامل | تأثیر |
|------|-------|
| تعداد عناصر | بیشتر = احتمال سود بیشتر |
| هزینه‌ی پردازش هر عنصر | سنگین‌تر = احتمال سود بیشتر |
| امکان تقسیم متوازن کار | بهتر = احتمال سود بیشتر |
| هزینه‌ی ترکیب نتایج | کمتر = احتمال سود بیشتر |
| تعداد هسته‌های قابل‌استفاده | بیشتر = احتمال سود بیشتر |
| رقابت بر سر منابع مشترک | کمتر = احتمال سود بیشتر |
| نیاز به حفظ ترتیب خروجی | کمتر = احتمال سود بیشتر |

<a id="prime-counting"></a>
## ۱۰. مثال موفق کتاب: شمارش اعداد اول تا $n$

$$ \pi(n) = \#\{p \leq n \mid p \text{ اول است}\} $$

**نسخه‌ی ترتیبی:**

<div dir="ltr">

```java
static long pi(long n) {
    return LongStream.rangeClosed(2, n)
        .mapToObj(BigInteger::valueOf)
        .filter(i -> i.isProbablePrime(50))
        .count();
}
```
</div>

**نسخه‌ی موازی:**

<div dir="ltr">

```java
static long pi(long n) {
    return LongStream.rangeClosed(2, n)
        .parallel()
        .mapToObj(BigInteger::valueOf)
        .filter(i -> i.isProbablePrime(50))
        .count();
}
```
</div>

**چرا این مثال مناسب است؟**

| دلیل | توضیح |
|------|-------|
| منبع داده | بازه‌ی عددی به‌راحتی تقسیم می‌شود |
| استقلال | بررسی اول‌بودن هر عدد مستقل است |
| عملیات پایانی | `count()` یک کاهش ساده است |
| ترکیب نتایج | نتایج جزئی به‌سادگی جمع می‌شوند |

**نتیجه‌ی اندازه‌گیری گزارش‌شده در کتاب ($n = 10^8$):**

| حالت | زمان |
|------|------|
| ترتیبی | ~۳۱ ثانیه |
| موازی | ~۹٫۲ ثانیه |
| بهبود | ~۳٫۴ برابر |

> **متن کتاب تقریباً ضریب ۳٫۷ را گزارش می‌کند.** هر دو عدد مربوط به اندازه‌گیری نویسنده روی سیستم خودش هستند، نه تضمین عملکرد روی هر سیستم.

> **نکته:** این مثال برای آموزش موازی‌سازی Stream ارائه شده است، نه به‌عنوان بهترین الگوریتم شمارش اعداد اول.

<a id="shared-pool"></a>
## ۱۲. یک pipeline موازی می‌تواند روی بخش‌های دیگر برنامه هم اثر بگذارد

> **بسیاری از pipelineهای موازی Stream از یک `ForkJoinPool` مشترک استفاده می‌کنند.**

```
                     ForkJoinPool مشترک
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
   Stream موازی ۱     Stream موازی ۲     Stream موازی ۳
   (درخواست A)        (درخواست B)        (درخواست C)
```

> **در سرویس‌های سمت سرور:** اگر هر درخواست یک Stream موازی سنگین اجرا کند، رقابت بر سر Threadها و منابع پردازنده ممکن است باعث افزایش تأخیر درخواست‌های دیگر شود.
