# ایجاد و نابودسازی اشیاء (Creating and Destroying Objects)

## آیتم ۱: استفاده از متدهای کارخانه‌ای استاتیک (Static Factory Methods) به جای سازنده‌ها (Constructors)

این بخش آغازگر فصل دوم کتاب با عنوان «ایجاد و نابودسازی اشیاء» است و به یکی از کلیدی‌ترین و معروف‌ترین مفاهیم کتاب یعنی **آیتم ۱** می‌پردازد.

جاشوا بلاک در این آیتم تأکید می‌کند که روش سنتی برای گرفتن یک Instance (نمونه) از کلاس، استفاده از کلمه کلیدی `new` و یک سازنده عمومی (public constructor) است. اما روشی بسیار هوشمندانه‌تر وجود دارد که باید در جعبه ابزار هر برنامه‌نویسی باشد: **متد کارخانه‌ای استاتیک**.

---

### مسئلهٔ اصلی چیست؟

در Java سنتی:

</div>

```java
new User(...)
```

<div dir="rtl">

راه استاندارد ساخت object بود.

جاشوا بلاک می‌گوید: `constructor` تنها گزینه نیست. بلکه:

</div>

```java
User.of(...)
User.from(...)
User.create(...)
```

<div dir="rtl">

در بسیاری موارد طراحی بهتری است.

<a id="advantages"></a>
## مزایای متدهای کارخانه‌ای استاتیک (Advantages)

<a id="advantage1"></a>
### ۱. برخلاف سازنده‌ها، این متدها «نام» دارند (They have names)

سازنده‌ها در جاوا مجبورند هم‌نام با کلاس باشند. این موضوع زمانی که نیاز به سازنده‌های مختلف با پارامترهای متفاوت داریم، فاجعه به بار می‌آورد.

- **مشکل سازنده‌ها:** کلاس `BigInteger` یک سازنده به شکل `BigInteger(int, int, Random)` دارد که یک عدد اولِ احتمالی تولید می‌کند. نام این سازنده هیچ توضیحی درباره کاری که انجام می‌دهد نمی‌دهد. چقدر قشنگ‌تر می‌شد اگر به صورت `BigInteger.probablePrime` صدا زده می‌شد؟

- **محدودیت امضا (Signature):** در جاوا نمی‌توان دو سازنده با پارامترهای ورودی یکسان (مثلاً هر دو دوتا `String` بگیرند) داشت. برخی برنامه‌نویسان با جابجا کردن ترتیب پارامترها این محدودیت را دور می‌زنند که یک Anti-pattern (روش بسیار بد) است، چون برنامه‌نویسان دیگر هرگز یادشان نمی‌ماند کدام به کدام است. اما متدهای استاتیک چون نام‌های متفاوتی دارند (مانند `createFromFirstname` و `createFromNickname`) این محدودیت را به راحتی حل می‌کنند.

#### مشکل Constructors چیست؟

مشکل اول:  
**Constructor Name ندارد**  
مثال:

</div>

```java
new BigInteger(128, 64, random);
```

<div dir="rtl">

این constructor چه می‌کند؟

- random number؟
- prime؟
- bit length؟
- seed؟

مشخص نیست.

#### Static Factory Version

</div>

```java
BigInteger.probablePrime(128, random);
```

<div dir="rtl">

فوراً semantic روشن می‌شود.

#### نکته مهم Architect-Level

Naming یکی از مهم‌ترین ابزارهای مدیریت complexity است.  
در سیستم‌های بزرگ:

- semantic clarity
- cognitive load reduction
- self-documenting APIs

بسیار حیاتی هستند.

#### مقایسه

| Constructor          | Static Factory       |
|----------------------|----------------------|
| syntax-oriented      | semantic-oriented    |
| ambiguous            | expressive           |
| overloaded confusion | named intent         |
| weak readability     | strong readability   |

#### مشکل Constructor Overloading

این بخش فوق‌العاده مهم است.

**مثال فاجعه‌بار**

</div>

```java
new User(String, int)
new User(int, String)
```

<div dir="rtl">

یا:

</div>

```java
new Color(int, int, int)
new Color(float, float, float)
```

<div dir="rtl">

**چرا خطرناک است؟**  
چون:

- compiler شاید اشتباه را detect نکند
- readability نابود می‌شود
- maintenance سخت می‌شود

**Production Problem**  
در enterprise systems، constructor overloading شدید، یکی از دلایل:

- onboarding difficulty
- API misuse
- subtle bugs

است.

<a id="advantage2"></a>
### ۲. نیازی نیست هر بار شیء جدیدی بسازند (Instance-controlled classes)

وقتی از کلمه کلیدی `new` استفاده می‌کنید، سیستم مجبور است یک شیء جدید در حافظه Heap ایجاد کند. اما متد استاتیک چنین محدودیتی ندارد.

- کلاس‌های غیرقابل‌تغییر (Immutable) مانند `Boolean` می‌توانند اشیاء از قبل ساخته شده را Cache (ذخیره‌سازی) کنند و همان‌ها را برگردانند. متد `Boolean.valueOf(true)` اصلاً شیء جدیدی نمی‌سازد، بلکه ارجاعی به شیء ثابتِ `Boolean.TRUE` که از قبل در حافظه هست برمی‌گرداند.

- این تکنیک شبیه به الگوی طراحی Flyweight است و اگر درخواست برای اشیاء تکراری و سنگین زیاد باشد، پرفورمنس را به شدت بالا می‌برد.

- این قابلیت به کلاس اجازه می‌دهد تا کنترل شدیدی روی نمونه‌های خود داشته باشد (Instance-controlled). به این ترتیب پیاده‌سازی الگوهای Singleton (تک‌نمونه) یا غیرقابل‌نمونه‌سازی (Noninstantiable) ممکن می‌شود. همچنین تضمین می‌کند که اگر دو شیء با هم برابرند (`a.equals(b)`)، آدرس حافظه آن‌ها نیز یکی باشد (`a == b`)؛ اتفاقی که در سیستم Enumها می‌افتد.

<a id="advantage3"></a>
### ۳. می‌توانند هر زیرنوعی (Subtype) از نوعِ بازگشتی خود را برگردانند

این مزیت دست شما را برای پنهان کردن کلاس‌های پیاده‌سازی (Implementation Classes) کاملاً باز می‌گذارد و به شما اجازه می‌دهد خروجی متد را از نوع یک Interface تعریف کنید.

- **مثال فریمورک Collections در جاوا:** کلاس `java.util.Collections` دارای ۴۵ پیاده‌سازی مختلف از اینترفیس‌ها (مثل لیست‌های غیرقابل تغییر، ست‌های همگام‌سازی شده و...) است. جاوا به جای اینکه ۴۵ کلاس عمومی بسازد و پکیج را شلوغ کند، همه این کلاس‌ها را به صورت private (غیر عمومی) در پشت صحنه نگه داشته و شما فقط از طریق متدهای استاتیکِ کلاس `Collections` (مثل `Collections.unmodifiableList`) به آن‌ها دسترسی دارید. این کار حجم مفهومی (Conceptual Weight) فریمورک را برای برنامه‌نویس بسیار کوچک و خوانایی را بالا می‌برد.

- **آپدیت جاوا ۸ و ۹:** تا قبل از جاوا ۸، اینترفیس‌ها نمی‌توانستند متد استاتیک داشته باشند؛ به همین دلیل یک کلاس همکار (Companion Class) مثل `Collections` برای اینترفیس `Collection` ساخته می‌شد. از جاوا ۸ به بعد، اینترفیس‌ها می‌توانند متد استاتیک عمومی داشته باشند (پس بهتر است متدها داخل خود اینترفیس قرار بگیرند). در جاوا ۹ نیز امکان تعریف متدهای استاتیکِ private به اینترفیس‌ها اضافه شد.

<a id="advantage4"></a>
### ۴. کلاسِ شیء برگردانده شده می‌تواند بسته به پارامتر ورودی تغییر کند

نوع شیء بازگشتی نه تنها می‌تواند یک Subclass باشد، بلکه می‌تواند از یک نسخه به نسخه دیگر جاوا بدون اینکه کد مشتری (Client) آسیب ببیند، تغییر کند.

- **مثال عینی (EnumSet):** کلاس `EnumSet` هیچ سازنده عمومی ندارد. در OpenJDK، وقتی شما یک `EnumSet` می‌سازید، متد استاتیک بررسی می‌کند: اگر تعداد عناصر Enum شما ۶۴ یا کمتر باشد، یک نمونه از کلاس `RegularEnumSet` (که پشت صحنه با یک متغیر long کار می‌کند و فوق‌العاده سریع است) برمی‌گرداند. اگر عناصر ۶۵ یا بیشتر باشند، یک نمونه از کلاس `JumboEnumSet` (که با آرایه‌ای از longها کار می‌کند) برمی‌گرداند. شما به عنوان کلاینت اصلاً روح‌تان هم از این تغییرات باخبر نمی‌شود و فقط با خود `EnumSet` کار می‌کنید.

<a id="advantage5"></a>
### ۵. کلاسِ شیء برگردانده شده نیازی نیست در زمان نوشتن متد وجود داشته باشد!

این ویژگی سنگ بنای معماری‌های قدرتمندی مثل Service Provider Frameworkها (به عنوان نمونه: JDBC در جاوا) است. در این سیستم‌ها، کلاینت کاملاً از پیاده‌سازی جدا (Decoupled) می‌شود.

یک سیستم Service Provider دارای ۳ بخش اصلی (و یک بخش اختیاری) است:

1. **Service Interface:** اینترفیسی که کار با سرویس را تعریف می‌کند (در JDBC: اینترفیس `Connection`).
2. **Provider Registration API:** متدی که شرکت‌های ثانویه (مثل اوراکل یا MySQL) برای ثبت پیاده‌سازی خود از آن استفاده می‌کنند (در JDBC: متد `DriverManager.registerDriver`).
3. **Service Access API:** همان متد کارخانه‌ای استاتیک انعطاف‌پذیر ما که کلاینت برای گرفتن نمونه سرویس صدا می‌زند (در JDBC: متد `DriverManager.getConnection`).
4. **Service Provider Interface (اختیاری):** فکتوریِ سازنده سرویس (در JDBC: اینترفیس `Driver`). اگر نباشد، از تکنیک Reflection استفاده می‌شود.

> نکته: از جاوا ۶ به بعد، خود پلتفرم دارای یک فریمورک عمومی به نام `java.util.ServiceLoader` است و دیگر نیازی نیست خودتان آن را بنویسید.

<a id="limitations"></a>
## معایب متدهای کارخانه‌ای استاتیک (Limitations)

<a id="limitation1"></a>
### ۱. کلاس‌هایی که سازنده public یا protected ندارند، نمی‌توانند Subclass شوند

اگر تمام سازنده‌ها را private کنید و فقط متد استاتیک بگذارید، دیگر هیچ کلاسی نمی‌تواند از این کلاس ارث‌بری (Inheritance) کند.

- البته جاشوا بلاک می‌گوید: این عیب می‌تواند یک «توفیق اجباری» (Blessing in disguise) باشد، زیرا برنامه‌نویسان را تشویق می‌کند که به جای ارث‌بری، از Composition (ترکیب) استفاده کنند که روش بسیار امن‌تری است. همچنین برای ساخت کلاس‌های Immutable الزامی است.

[بازگشت به بالا](#top)

<a id="limitation2"></a>
### ۲. پیدا کردن آن‌ها در مستندات کد (Javadoc) سخت‌تر است

سازنده‌ها در مستندات Javadoc جایگاه مشخص و برجسته‌ای دارند و سریع دیده می‌شوند، اما متدهای استاتیک کارخانه‌ای در میان انبوه متدهای دیگر کلاس گم می‌شوند. برنامه‌نویس ممکن است در نگاه اول متوجه نشود چطور باید از کلاس شیء بسازد.

- **راه‌حل:** برای حل این مشکل باید از نام‌گذاری‌های استاندارد و رایج در جامعه جاوا استفاده کنید.

<a id="naming-conventions"></a>
## اصطلاحات و کنوانسیون‌های رایج نام‌گذاری

برای حل مشکل پیدا شدن متدها، همیشه از این نام‌های استاندارد استفاده کنید:

| نام متد | کاربرد | مثال |
|---------|--------|-------|
| `from` | تبدیل نوع (Type conversion) با یک پارامتر ورودی | `Date d = Date.from(instant);` |
| `of` | تجمیع (Aggregation) چندین پارامتر ورودی | `Set<Rank> faceCards = EnumSet.of(JACK, QUEEN, KING);` |
| `valueOf` | جایگزین پرجزئیات‌تر برای `from` و `of` | `BigInteger prime = BigInteger.valueOf(Integer.MAX_VALUE);` |
| `instance` یا `getInstance` | برگرداندن یک نمونه بر اساس پارامترها (احتمال دارد شیء تکراری یا از قبل ساخته شده باشد) | `StackWalker luke = StackWalker.getInstance(options);` |
| `create` یا `newInstance` | مثل نمونه قبلی، با این تضمین که هر بار یک شیء کاملاً جدید ساخته و برگردانده می‌شود | `Object newArray = Array.newInstance(classObject, arrayLen);` |
| `getType` | شبیه `getInstance` است، اما زمانی استفاده می‌شود که متد استاتیک در یک کلاس دیگر قرار دارد (`Type` نوع شیء خروجی است) | `FileStore fs = Files.getFileStore(path);` |
| `newType` | شبیه `newInstance` است، اما وقتی متد در کلاس دیگری قرار دارد | `BufferedReader br = Files.newBufferedReader(path);` |
| `type` | نسخه مختصر و کوتاه‌شده `getType` و `newType` | `List<Complaint> litany = Collections.list(legacyLitany);` |

## نتیجه‌گیری آیتم ۱

هر دو روش (سازنده‌ها و متدهای استاتیک) کاربرد خود را دارند. اما در بسیاری از مواقع، متدهای استاتیک برتری‌های خیره‌کننده‌ای دارند. بنابراین، این عادت بازتابی (Reflex) که برای هر کلاس سریعاً یک سازنده public بسازید را کنار بگذارید و اول به متدهای کارخانه‌ای استاتیک فکر کنید.
